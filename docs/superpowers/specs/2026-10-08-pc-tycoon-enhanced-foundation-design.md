## 1. 意図と到達目標

プレイヤーがスタートアップから技術企業を育て、PC部品・完成PC・OS・LLMを研究、設計、開発、製造／提供、販売し、競合と争う経営ゲームを作る。

**成功基準**:
1. ブラウザ（デスクトップおよびモバイル）で遊べる。
2. 主要な設計判断が製品性能・原価・需要・評判・売上・次の研究に実際に影響する。
3. PC Tycoon 2 の公開資料で確認できるゲーム要素を機能単位で網羅し、非公開部分の推測は区別する。
4. LLM の設計と商業化は架空モデルの**数値シミュレーション**で実現し、AIモデルの実学習／実推論は行わない。
5. インターネット接続なしでもゲームが成立し、セーブ／ロード／エクスポート可能。
6. PC Tycoon 2 のタイトル・素材・コード・固有の画面構成をコピーせず、独立のUIとアートで制作する。

これは最終到達目標であり、初期リリースですべてを満たすという意味ではない。

## 3. 方式比較と推奨

### A: Webファースト（推奨）
- TypeScript（厳格な型チェック）、Vite、ReactでUIを構築。
- UI非依存の決定論的TypeScriptエンジンでゲームを進行。
- PWA + IndexedDBでオフラインとローカル保存に対応。
- CapacitorでAndroid APKを同一コードベースからパッケージ。
- 長所: 開発・テスト・ブラウザ公開が容易、スマホ対応を共通化できる。
- 短所: 3Dオフィスの表現力は専用ゲームエンジンより調整が必要。必要なら限定的にThree.jsを使う。

### B: Godot
- 長所: 2D/3D演出とゲーム用操作に強い。
- 短所: 膨大な帳票・設定フォームの制作、およびブラウザ上の情報量の多いUIが相対的に重い。

### C: Unity
- 長所: 3Dオフィスとデスクトップ／Android向け制作に向く。
- 短所: Web配信容量・ロードとモバイルブラウザの要件が重い。

**設計判断**: ゲーム内の設計・経営・分析が中心のためAとする。リッチな施設ビジュアルはコアが動作した後に追加する。

## 4. モジュール境界

```
[React UI + 入力 + アクセシビリティ]
                |
         [Game Commands]
                |
[Simulation Core / 純粋な状態遷移 / seed PRNG]
  |       |          |             |
[研究] [製品設計] [経済・市場] [LLM/AI]
  |       |          |             |
  +-------+----[競合・雇用・工場]--+
                |
        [状態スナップショット]
                |
 [IndexedDB セーブ / JSON 入出力]
```

1. `packages/sim`: TypeScriptのみ。ブラウザAPI非依存。状態スキーマ、時間進行、経済、製品、競合、AI数値計算、検証、イベント。
2. `apps/web`: React/ViteのUI。コンポーネント、チャート、ゲームメニュー、i18n、キーボード・タッチ操作、PWA登録。
3. `apps/android`: CapacitorのAndroidラッパー。Web版とゲームデータ仕様を共有。
4. `packages/content`: 技術・部品・イベント・人材・競合テンプレート・バランス設定。データは実装コードから分離。
5. `packages/save`: バージョン付き保存、IndexedDB、JSONエクスポート・インポート、マイグレーション。
6. `docs`: ゲーム仕様、原作対応、係数の根拠、開発計画、検証記録。

**データの流れ**: UIは検証済みコマンドを送る。シミュレーション側が合法性（資金・研究・互換性・施設条件）を検証して状態を更新する。市場と競合は日／週／月の決定論的 tick で処理し、各tickで発生した事象をイベントログ化。UIは結果のみ表示する。

## 5. ゲーム進行の共通規則

- 新規開始時に社名、開始年代（シミュレーション内の時間）、難易度とシードを設定する。初期資金や技術水準はコンテンツで定義する。
- プレイヤーは時間を一時停止・1x・高速で進められる。バックグラウンド実時間を勝手に換算しない。
- `daily`: 需要、稼働率、在庫、生産進捗、LLM推論需要。
- `weekly`: 製品売上、広告効果、研究進捗、モデル学習進捗。
- `monthly`: 給与、固定費、施設費、売上総括、競合の戦略更新。
- 従業員、資金、研究、設備、製造枠は共有する有限資源。支出超過は明示的に拒否するか、許可された借入残高として表現する。
- 市場需要は性能・価格・信頼性・評判・ブランド認知・発売時期・用途適性・競合供給に依存する。
- ランダム事象はシード付き擬似乱数。等しい初期状態、シード、コマンド列なら同じ結果。
- ゲームバランス係数は全て設定データ化し、架空のゲーム数値と実世界の工学指標をUIで区別する。

## 6. PC開発と経済

### ハードウェア
- 製品カテゴリ別の制約付きスペックフォーム。性能指標・消費電力・製造原価・研究所要量・製造難度が変化。
- CPU: 世代、コア構成、周波数、IPC相当、プロセス、消費電力など。
- GPU: 演算資源、周波数、VRAM、帯域、電力、AI計算適性。
- その他: マザーボードの互換性、RAMの世代／速度／容量、SSD等の容量／速度、モニターの解像度／リフレッシュレート／色域。
- ノートPC・デスクトップ・サーバー: パーツ互換性を守り用途別スコアを付与。製品の外観は既製パーツと独自の意匠選択からゲーム独自に組む。
- 発売: 研究完了→設計→生産ライン割当→在庫→価格設定→販売→次世代モデル。

### OS
- 自社OSの開発、互換API／ドライバ対応、機能選択、更新、サポート品質、ライセンス価格を扱う。
- **操作テスト**はゲーム内で描画する架空デスクトップとし、現実のOSエミュレーションとは区別する。
- アプリの可用性はゲーム内互換性ルールで決まり、OS市場とPC製品に相互作用する。

### 会社運営
- オフィス10段階、工場の生産能力・稼働費、雇用／人材能力／採用費、研究予算、マーケティング、買収。
- 複数競合が製品を開発し、独立した在庫・資金・研究・価格戦略を持つ。
- 売上、営業費、資本支出、現金、粗利益、商品別実績、シェア、市況を可視化する。
- 難易度は需要変動・競合効率・開始資金・借入条件・研究費等に作用し、既存セーブの難易度と独立に保存する。

## 7. LLM設計・学習・推論のシミュレーション

ユーザーが選択した **A案**。架空の会社・モデル・ベンチマークをゲームとして扱う。現実のLLMを訓練、重み生成、ダウンロード、推論しない。

### 設計パラメータ
- Dense / MoE
- 総パラメータ数 `P_total` と実行時稼働数 `P_active`（Denseでは両者一致、MoEでは `P_active <= P_total`）
- 層数、hidden size、attention系統、コンテキスト長
- データ量（学習トークン数）、品質、多様性、データ取得コスト
- 学習ハードウェア（GPU性能／VRAM／枚数、電力、ネットワーク効率）、予算、期間
- 推論時の量子化ビット、バッチサイズ、API単価、提供形態

### 簡略化されたゲーム内の計算規則（調整可能）
- 学習計算量の初期近似: `F_train ≈ 6 × P_active × T` FLOP。これはゲームの初期係数であり、実モデル学習時間の正確な予測値ではない。MoEルーティング、Attention長、並列通信等は別の効率係数で調整する。
- 予想学習時間: `F_train / (cluster_peak_FLOPs × efficiency)`。GPU仕様と冷却、データセンター／通信のボトルネックを反映する。
- 重み保存容量の下限の概算: `P_total × bits / 8` bytes。推論に必要なKVキャッシュとその他の予約メモリを別に加算。MoEでもパラメータ総量に基づくメモリ要件を維持する。
- ベンチマーク: 計算予算に対する飽和型効果、データ品質・トークン量・技術解放・アーキテクチャ適性を合成。数学、コーディング、知識、推論、多言語の各スコアを別々に決める。単にパラメータ数を増やしても勝てないバランスを目指す。
- サービス原価: 推論トークン需要、実効トークン毎秒、GPU占有、設備投資償却、電力、運用を組み合わせる。推論の量子化はメモリと速度を改善し得るが品質ペナルティもあり得る。
- 売上: `API使用量×価格 + 定額プラン契約収入 - 返金・手数料`。利益評価にはインフラ費と研究費を含める。
- 無効条件は検証ルールで制御: 例）未研究の技術、使用可能VRAM不足、負のトークン数、予算不足、非現実的なパラメータ構成。

### PC事業との結合
- 自社GPUとサーバーを学習クラスタに投入できる。ただし他社製GPU購入の選択肢も残す。
- 強力なAI製品は自社GPU／サーバーの需要に寄与する。ハードウェア企業によるAI事業は新収益源となる一方、計算設備・人件費・学習失敗のリスクを負う。
- ゲーム内ベンチマークは「架空」と明示。実製品の商標、正確性が検証されていないランキングを実際の数値として示さない。

## 9. 保存・失敗時の扱い

- 各ゲームに固有のセーブID、スキーマバージョン、シード、直近tick、全状態を持たせる。
- IndexedDBへの保存は一貫したスナップショット単位で更新。未完了書込みによる破損を回避。
- JSONエクスポート／インポートは形式・サイズ・スキーマを検証し、不正データは既存セーブを破壊せず拒否する。
- アップグレード時のマイグレーション、最大保存容量、保存失敗の明示、ストレージ不足時の案内を準備。
- 起動時には最後の有効な保存データから復元。自動保存は固定tickまたは重要な変更後に実行。
- バックエンドなしで主要機能を完結させ、ユーザーデータを外部送信しない。

## 11. テストと品質ゲート

- 純粋なシミュレーションロジックには単体／プロパティテストを適用。
- ケース: 無資金の購入を防止、商品互換性、在庫非負、赤字による現金状態、研究の前提条件、時間進行、競合の独立意思決定、数量・価格の境界値。
- **決定論**: 同一初期状態＋同一シード＋同一コマンド列ならtick／売上／競合結果が完全一致。
- **LLM**: DenseとMoEの `P_active` の整合性、VRAMと量子化によるコストの単調性のある範囲、計算コストの正値、過剰な性能インフレーション防止。
- **セーブ**: 保存→復元→同じ後続操作の一致、異常JSONの拒否、旧スキーマからの移行。
- **統合**: 研究→設計→製造→発売→売上→再投資が終了まで成功。
- **UI**: PCブラウザとAndroid幅、タッチ、キーボード、長いリスト、ゲーム進行速度、オフライン動作。
- **配布**: PWAのビルドとオフライン確認、Capacitor APKのビルドとAndroid実機起動（実機がない段階は未確認のまま報告）。
- すべてのフェーズでテストを記録し、未検証項目を未検証として扱う。

## 12. リスク・制約・非目標

1. **網羅の定義**: 公開資料による機能群は確認できるが、隠れた細部の完全同等性までは証明できない。対応表を公式資料／ゲーム内確認で更新。
2. **工数**: PC Tycoon 2 の全ゲーム要素＋独自LLMは大規模。F0を最小限の遊べるゲームに限定し、段階的に拡張する。
3. **3000技術**: 3000個の無意味な数字の水増しをしない。体系化した技術カテゴリ／世代／分岐と独自効果で構成し、内容・バランスの自動検証を行う。
4. **リアリズム**: GPU・LLM・市場モデルはゲーム用近似。実世界の性能・費用・競争を正確に予測する目的には使用しない。
5. **知的財産**: 原作のUIや画像、ゲームデータを流用せず、同ジャンルの独自ゲームにする。
6. **APK**: Android用の署名・配布・実機検証は後段。ブラウザでの完成がAPK完成を保証するものではない。
7. **ネットワーク**: 初期版でサーバー、クラウドアカウント、マルチプレイヤー、実LLM APIは作らない。

## 13. 設計レビューで確定したい事項

- 基盤とゲームエンジンはWebファースト（React/TypeScript）で進める。
- 初期からPC・スマートフォン双方で操作できるUIとする。
- 上記フェーズ順で基盤→ハード→OS→経営→LLM→コンテンツ充実→配布とする。
- ゲームのリアリズム優先度は「業界のトレードオフを反映するが、遊びやすさを優先する」とする。

**次の工程**: この文書のレビュー後、Superpowers `writing-plans` で **F0のみ** 詳細な実装計画を作成。計画レビューと実行方法の承認を受けてからコード実装へ進む。
